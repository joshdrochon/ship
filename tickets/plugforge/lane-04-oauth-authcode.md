**Where PKCE is validated is already marked, and this lane is what makes the mark true.**
`docs/architecture.md:115` reads *"★ PKCE validated HERE — S256(verifier) ≟ stored challenge. Mismatch
→ 400 invalid_grant (mandatory negative Playwright test)"*, sitting on the `/oauth/token` participant
of the Auth Code sequence diagram. That is a graded deliverable (p.12's OAuth Flows row requires the
diagram to *"Mark where PKCE verifier is validated"*), so the assertion point is not a choice this
lane makes — it is a commitment this lane keeps. PF-101 is the ticket; PF-113 is the test that fails
if the diagram and the code ever disagree.

**D4 arrived settled and PF-099 clears L03's `⚑`.** L99 closed it 2026-08-12: **re-consent with
union**. A new scope restarts `/oauth/authorize`, the user consents to the full union, and a fresh
token replaces the old one. No mutable grant records and no incremental-consent bookkeeping. L03's
PF-076 assumed exactly this and flagged itself pending the decision; PF-099 implements the authorize
half, and the flag comes off. p.16 asks the question (*"does a user who originally granted
`documents:read` need to re-consent to grant `documents:write`, or do you support incremental
consent?"*) and L25's PF-758 carries the written answer as a deliberate cut.

**The one thing this lane will not do: route OAuth errors through the public envelope.** L99's **U3**
is a verified finding, not an opinion — the PRD's only `400` (`invalid_grant`, p.2) is RFC 6749 §5.2's
error format on `/oauth/token`, which `createApp()` mounts at `app.use('/oauth', …)`, outside
`/api/v1` entirely. L07's `ApiError` union is six codes (`unauthorized`, `forbidden`, `not_found`,
`validation_failed`, `rate_limited`, `server_error`, p.7) and `invalid_grant` is in none of them, nor
is 400 in L07's status map. Wrapping the OAuth error in `ApiError` would ship a contract violation
that every RFC-compliant client — including the browser demo and any grader's OAuth library —
would fail to parse. PF-106 tickets the separation and PF-107 tickets the middleware consequence.

**The sketches are spikes.** `api/src/platform/oauth/pkce.ts` is 24 lines of correct, untested S256
helpers (`s256Challenge`, `verifyPkce`, `isValidVerifier`) and is the closest thing on disk to done —
PF-101 keeps it and tests it. `api/src/platform/oauth/router.ts` is a `TODO(josh)` list returning an
empty `Router()`. Nothing else exists: there is no authorize handler, no consent screen, no
authorization-code table, and no migration.

## Notes for the audit agent

Read the full PRD, not just the pages cited above. Known thin spots and the calls made, so you can
confirm or refute rather than rediscover:

- **PF-094 is the decision this lane owns and it is a real one.** p.16 offers *"a route inside Ship's
  UI, a dedicated endpoint with its own minimal layout, or something else"* and I took the middle
  option. The argument that decided it is not taste: routing the authorize leg through the Vite SPA
  puts the MVP gate's own Playwright test behind SPA hydration, and `playwright.config.ts:60` retries
  twice in CI (L99 **F27**), so hydration flake gets retried into a pass and the gate test stops being
  a gate. The counter-argument, which is fair: a server-rendered HTML template is the only non-React
  UI in the repo and someone has to keep it looking like Ship. If the audit prefers the React route,
  the change is confined to PF-094/095/096 — but the PR that makes it must also pin `retries: 0` on
  the gate test, or it is trading a visual consistency win for a silently unreliable gate.
- **The clickjacking answer is headers on a response, deliberately not a helmet setting.** PF-096
  asserts `frame-ancestors 'none'` and `X-Frame-Options: DENY` on both consent methods and proves it
  in a framed browser. I wrote it that way because helmet is configured once in `createApp()` for the
  whole app and its defaults do not set `frame-ancestors 'none'`; a lane that "relies on helmet" is
  relying on a config another lane can change without failing any test. Re-check that helmet claim
  against `api/src/app.ts` at audit time — it is the one repo fact in this ticket I would most expect
  to have drifted.
- **U3 is settled here in one direction and it needs L05 and L06 to hold the same line.** PF-106
  makes `/oauth/*` an RFC 6749 §5.2 error surface with its own Zod oracle and forbids the `ApiError`
  envelope on it. L05's device endpoints and L06's refresh grant are on the same router and must use
  the same schema — I have named the seam in both files' notes, but if the audit finds either lane
  importing L07's `ApiError` for an OAuth failure, that is the contract violation U3 predicted and it
  is worth failing a PR over. The mirror-image mistake is also worth checking: nothing on `/api/v1`
  may emit `invalid_grant`, and PF-106's second fitness test is what catches it.
- **PF-107 records a consequence rather than a fix, on purpose.** Because `/oauth` is mounted outside
  `/api/v1`, L12's audit middleware never sees a token exchange — which is precisely the measured gap
  L02's PF-050 built `recordSecretAuth` to fill. I did **not** ticket an audit row for the authorize
  or token endpoints in this lane, because that would be a second audit sink with a second schema
  answering the same p.17 question. If the audit thinks the OAuth endpoints need their own trail
  beyond PF-050's secret-auth signal, that is a cross-lane finding for `lane-99-unassigned.md`, not a
  local addition here.
- **PF-104's revocation-on-replay is stricter than the PRD and I think it is right.** The PRD says
  nothing about a replayed authorization code; RFC 6749 §4.1.2 says the server SHOULD revoke tokens
  previously issued from it. I took the SHOULD, because the alternative leaves one theft-response
  story for refresh tokens (p.3's *"reuse invalidates the family"*, L06's PF-168) and a different,
  weaker one for codes — and a grader asking *"what happens if a code leaks"* gets a worse answer for
  no saving. This is the ticket most likely to be called scope creep; the citation is p.10's
  *"IETF-correct"* and I would defend it, but it is a judgement.
- **What I deliberately did not claim.** **MVP-3** (bearer middleware, distinct 401 codes) is L06's
  even though PF-108 uses a token against `/api/v1/documents` to prove "usable" — that assertion
  rides on L06's PF-158 and L09's PF-245, both named in `Deps`. **TS-3** is L19's PF-564 with L05's
  server half; nothing here touches the device grant. The `client_credentials` grant the `router.ts`
  spike lists for the first-party agent is **L05/L23's** territory under L99's D5a, and no ticket here
  assumes a grant type for the seeded agent app. And the token issuance itself — access-token minting,
  refresh pairing, TTLs — is **L06's PF-155**, which PF-100 calls rather than reimplements.
- **`Advances` distribution and the three blanks.** `MVP-2` on nine tickets (the gate item this lane
  exists to close), `MVP-6` on three (jointly with L03, which owns the registry and the 403 body),
  `TS-2` on two, `CTR:*` on seven (Authorization Code + PKCE ×5, OAuth App Model ×1, Consistent Error
  Shape ×1, Public API Boundary ×1), `PERF:` on one — p.6's *"OAuth Auth Code + PKCE round-trip
  (P95)"* row is graded, is owned by no other lane, and the spine's taxonomy has the prefix for
  exactly this case — `SUB:*` on two, and `—` on three (PF-092 `state` echo, PF-110 Playwright
  stability, PF-112 the sweeper). Each blank is real plumbing behind another ticket's citation and
  none of them should carry graded credit in a PR body.
- **What I could not ticket.** First, **`/oauth/authorize` has no rate limit and I did not invent
  one.** PF-107 asserts the internal `apiLimiter` does not reach `/oauth/*` and L11's limiter is
  scoped to `/api/v1` by construction, so the authorize and token endpoints are unthrottled. p.4's
  rate-limit row is explicitly about *"Public responses"* carrying `X-RateLimit-*`, which these are
  not, and inventing a limiter here would put a third rate-limiting implementation in the repo. It is
  a real exposure (a token endpoint is a credential-stuffing target) and it belongs in
  `lane-99-unassigned.md` as a cross-lane question for L11, not as a ticket I write alone. Second,
  **token revocation has no endpoint** — RFC 7009 is not in p.10's list (which names 6749, 7636 and
  8628 and stops), so a user cannot revoke a grant from the UI; L06's PF-165 gives the *repository*
  the ability, and the missing surface is a product gap, not a graded one. Third, **`prompt` /
  `max_age` / silent re-authorization**: the PRD never mentions them and D4's re-consent-with-union
  means every upgrade shows a screen, which is the simplest correct behaviour.
