**This is the flow the demo actually runs.** p.6's five-line story opens
`ship login   # Device flow`, p.11's Build Strategy §7 makes the CLI *"the proof the platform
works"*, and p.8's drill table has an Auth stage whose expected outcome is *"User code displayed;
polling succeeds within 60s in tests; token persists in configured store."* Every one of those runs
through the three endpoints in this lane. p.11 also sets the schedule: *"Device Authorization Grant
follows the same day"* as Auth Code + PKCE.

**What the PRD actually specifies, and what it does not.** p.3's Device Authorization Grant row is
three clauses: *"`/oauth/device/code` issues a `user_code` and `device_code`; `/oauth/device/verify`
accepts the `user_code`; the client polls `/oauth/token` until authorized. Slow-down responses
honored."* That is the whole normative text. **`verification_uri`, `interval` and `expires_in` do not
appear anywhere in the PRD** — verified by grep across all eighteen pages. They come from two places
this lane is entitled to cite: `docs/architecture.md:128` (*"`device_code, user_code,
verification_uri, interval`"*, a graded deliverable already committed), and p.10's stack row, which
requires *"Hand-rolled minimal IETF-correct flows (RFC 6749 + 7636 PKCE + 8628 Device Grant)"*. p.7's
SDK signature `onUserCode: (code: string, verifyUrl: string) => void` independently proves the client
is handed a URL as well as a code. Tickets that rest on RFC 8628 rather than on PRD prose say so.

**Errors on this router are RFC 6749/8628 shapes, not `ApiError` — settled in L04.** L99's **U3** and
L04's **PF-106** establish that `/oauth/*` emits `{error, error_description?}` with RFC codes and
never the public envelope. The device grant adds `authorization_pending`, `slow_down`,
`access_denied` and `expired_token` (RFC 8628 §3.5) to that set. PF-142 extends L04's Zod oracle
rather than declaring a second one.

**No sketch exists for this lane.** `api/src/platform/oauth/router.ts` lists
`POST /oauth/device/code` and `GET /oauth/device/verify` in a `TODO(josh)` comment and returns an
empty `Router()`. There is no device-code table, no `user_code` generator, and no polling logic
anywhere in the repo.

| — | ⚑ **A one-threshold invalidation clause would have been dead code** | — | PF-132 asks that a `user_code` *"guessed at past the threshold is invalidated rather than left live."* Implemented with a single threshold this is **unreachable**: the attempt that crosses it also starts the cooldown, so every later attempt is refused before any lookup happens and a found code is never observed. It would read as a control and be dead code — worse than absent, because a reader counts it as protection. Shipped with two constants: block at 5 (`USER_CODE_MAX_FAILURES`), treat a success as a guess at 3 (`USER_CODE_SUSPICION_FAILURES`). A test asserts `SUSPICION < MAX` and that a suspect key is still *allowed*, which is what keeps the branch reachable. Caught by the test failing, not by review. |

## Notes for the audit agent

Read the full PRD, not just the pages cited above. Known thin spots and the calls made, so you can
confirm or refute rather than rediscover:

- **TS-3 is a declared split, and I want the audit to check it is a split rather than a duplicate.**
  L19's **PF-564** claimed Testing Scenario 3 board-wide because the scenario's subject is literally
  *"a test CLI"*, and its note says the claim cannot go green until this lane lands and asks that any
  L05 scenario ticket be split explicitly — *"server honors `slow_down` / client obeys it"* — rather
  than duplicated. **PF-138 is that server half** and it asserts over HTTP with no CLI in the picture;
  PF-564 asserts the real binary's behaviour with the real SDK. Both cite `TS-3`, the same way L24's
  PF-730 and L16 both cite `TS-8` for the wire and portal halves of one scenario. If the audit reads
  this as double-counting, demoting PF-138 to `CTR:Device Authorization Grant` costs nothing — but
  then re-point PF-564's `Deps` at PF-138, because today that cell deliberately contains no L05 id.
- **PF-128 is the open decision this lane surfaces and it is genuinely open.** p.16 asks whether users
  paste a code or click a URL and says RFC 8628 allows both. I chose both-with-the-form-normative, and
  the load-bearing part is not which one ships — it is that `verification_uri_complete` still renders
  the code and asks the user to confirm it matches their terminal. Without that confirmation the
  completed URI is a one-click device-phishing primitive (RFC 8628 §5.4), and it would be very easy to
  ship it without, because the flow "works" either way. If the audit or the user prefers form-only,
  the change is one field in PF-122's response and one branch in PF-129; the demo gets slightly worse
  and nothing else moves.
- **Three fields in PF-122 are not in the PRD and the ticket says so.** I grepped all eighteen pages:
  `verification_uri` appears in none of them, and neither do `interval` or `expires_in`. They are in
  `docs/architecture.md:128` — a graded deliverable that already committed to them — and in RFC 8628
  §3.2, which p.10 makes normative by requiring *"Hand-rolled minimal IETF-correct flows (RFC 6749 +
  7636 PKCE + 8628 Device Grant)"*. p.7's `onUserCode(code, verifyUrl)` is independent corroboration
  that the client gets a URL. I did not want a ticket resting on a citation that a grep would not
  return, so the provenance is written into the ticket rather than smuggled into the `PRD` column.
- **PF-135 and PF-136 are where a hand-rolled device grant is usually wrong, and both are cheap to
  wave through.** `authorization_pending` returned as `200 {"status":"pending"}` feels natural and
  breaks every compliant client; `slow_down` returned without raising the stored interval leaves a
  fast client in a permanent error loop. Both pass a casual reading of p.3's *"Slow-down responses
  honored"* and both fail the drill. If the audit checks two things in this file, check these.
- **PF-132's throttle exists because nothing else throttles this router, and I verified that.** L11's
  limiter is scoped to `/api/v1` by construction, and L04's PF-107 asserts the internal `apiLimiter`
  mounted at `app.use('/api/', …)` does not reach `/oauth/*`. So the `user_code` guess space — which
  PF-123 deliberately made small and typeable — is defended by this lane's own counter and by nothing
  else. If the audit finds L11 extending to `/oauth`, PF-132 should become a configuration of that
  limiter rather than a second mechanism, and the ticket should shrink rather than be deleted.
- **What I deliberately did not claim.** **MVP-3** and the bearer middleware are L06's; PF-138(c)
  asserts a device-grant token works on `/api/v1/me`, which rides on L06's PF-158 and L10's PF-271,
  both named in `Deps`. **MVP-2/TS-2** are L04's — nothing here touches PKCE. **`client_credentials`
  for the seeded agent app** is L99's D5a and belongs to L23's rewire; the `router.ts` spike lists it
  and I left it there, because a grant with no browser step is not this lane's flow even though it
  shares the endpoint. Token TTLs, refresh rotation and family revocation are **L06's PF-155–PF-176**;
  PF-140 calls the issuance site and asserts this lane mints nothing.
- **`Advances` distribution and the two blanks.** `CTR:Device Authorization Grant` on twelve tickets
  (the p.3 row this lane exists to satisfy), `TS-3` on one (split with L19, above), `MVP-6` on one

- **What I could not ticket.** First, **there is no way for a user to see or revoke an authorized
  device.** RFC 8628 has no such requirement, the PRD never mentions one, and p.10's flow list stops

  machine has no surface to undo it; L06's PF-165 gives the repository the capability and no route
  exposes it. That is a product gap, not a graded one, and inventing the endpoint here would be scope
  creep by the spine's own rule. Second, **the `user_code` entropy figure is a decision without a
  requirement**: PF-123 fixes a charset and a length and PF-132 fixes a throttle, and RFC 8628 §5.1

  reasoning rather than citing a target that does not exist. Third, **nothing measures how long a
  human actually takes** between seeing the code and approving it, which is what would justify or
  refute PF-127's 600 s; L20's drill measures the automated path only, and the honest note is that the
  number is RFC 8628's example rather than an observation.
