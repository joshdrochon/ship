**What this lane owns.** The last epic and, in the PRD's own framing, the point of the week —
p.11 calls the rewire *"the architectural payoff"* and p.1 says the agent *"stops being a
privileged insider and becomes a platform citizen."* Concretely: the agent authenticates as a
first-party OAuth app, reads Ship state through `@ship/sdk` → `/api/v1/*` instead of direct SQL,
and its two write actions become recommendations, because **D5b makes it read-only**. The audit
trail is what proves it, and this lane owns the test that proves it stays proved.

**Two decisions arrive settled, and one of them changes what the agent does.**

| | Decision | Consequence for this lane |
|---|---|---|
| **D5a** | Client Credentials (RFC 6749 §4.4) | The agent runs on a schedule with no user at the keyboard; Device and Auth Code both need a human browser step a cron job cannot perform. **L04/L05/L06 are unwritten and none of them owns this grant** — so PF-686–688 ship it here |
| **D5b** | Read-only: `documents:read`, `issues:read`, `sprints:read` | The agent's `comment` and `history_note` actions have no public route and no scope. They become recommendations in `fleetgraph_notifications`. That is a real behavioral change to Part 2's agent, and PF-704–708 are about proving it honestly |

**The measurement D5b rests on, re-taken in this pass — and the brief was one endpoint off.**
The agent has exactly three action kinds: `comment`, `history_note`, `notify`
(`agent/src/actions/act.ts:74,77,83`). The first two reach Ship over HTTP through
**`POST /api/documents/:id/comments`** and **`POST /api/issues/:id/history`** — the two members of
`ShipRequest` in `agent/src/actions/client.ts:147–149`, pinned by an allowlist regex at `:187`.
`PATCH /api/issues/:id` appears in `act.ts` only inside the *refusal string* for mutations
(`:66–69`), which never executes a request. The correction does not weaken B12; it strengthens it,
because it adds `documents/:id/comments` to the list of write routes the public API does not have.
Verified: nothing in `lane-09-resource-documents.md` ships a comment route (PF-245–247 are list /
get / create only, and PF-265 asserts `documents` is the *only* resource mounted) and nothing in
`lane-10-resource-rest.md` ships a history route (PF-277–286 are issues, sprints and `me`). The
seven scopes on p.3 name neither. `notify` already writes `fleetgraph_notifications` over SQL and
sends no HTTP at all (`act.ts:83–87`), so it is untouched by any of this.

**Which is exactly why Epic 7's claim becomes literally true.** With no write path, the agent's
public-API traffic is entirely reads under its own `client_id`, and the recommendation rows live in
its own tables — so there is no third channel through which the agent reaches Ship data. p.18 asks
how you would tell, post-demo, *"the agent actually went through the public API for every action"*;
PF-697 makes "every" a checkable invariant rather than an adjective.
