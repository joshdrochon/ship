**Two marks in `docs/architecture.md` are this lane's contract, not its choices.**
Line 118 sits on the `/oauth/token` participant of the Auth Code diagram: *"★ rotation HERE — new pair
issued, old spent. Reuse of a spent refresh token revokes the whole family (theft signal)"*, and p.12
requires the diagram to *"Mark … where refresh-token rotation happens."* Line 138 reads *"Access
tokens are opaque high-entropy strings stored hashed (same discipline as the existing `api_tokens`
table); the bearer middleware resolves token → app + user + granted scopes on every `/api/v1/*`
request."* Both are graded deliverables already committed. PF-152 and PF-166 implement them; PF-176 is
the test that fails if the code and the document ever disagree.

**The SDK's refresh model is closed and this lane is the other half of it — consume, do not
re-decide.** L99's **D8** was closed by L17/L18: the store persists **both** access and refresh
tokens (PF-504), and refresh is a **single-flight promise** keyed to the token store (PF-509), because
p.3 mandates one-time-use refresh tokens with family revocation and *"two parallel refreshes present
the same refresh token twice and the second **revokes the family**, logging the user out."* That is a
statement about **this lane's** server behaviour. PF-170 makes rotation atomic so the race has one
deterministic outcome rather than two racing writers, and **PF-171 raises the residual the
single-flight promise cannot cover** — two *processes* sharing one credential file, which is exactly
what L19's PF-566 file store makes normal for the CLI. That residual is a policy decision and it is
escalated rather than quietly chosen.

**The distinct expired-token code has nowhere obvious to live, and that is a real design constraint.**
p.2 requires *"expired tokens return 401 with a distinct error code"*, but L07's `ApiError` union is
six codes (p.7) and the only 401 in it is `unauthorized`. Adding a seventh code would break L17's
6→5 kind mapping (PF-498 asserts key-equality against `API_ERROR_CODES`) and L07's closed union. So
the distinction lands in `details`, machine-readably, exactly as L03's PF-069 puts `required_scope`
in `details` for the 403 rather than inventing a code. PF-161 is the ticket and it states the
reasoning, because "we used `details`" reads as a dodge unless the alternative is written down.

**Nothing exists on disk.** `api/src/platform/apps/types.ts` declares an `IssuedTokens` interface with
the right shape and a comment that access tokens are *"~1h TTL"*; `api/src/platform/oauth/router.ts`
lists refresh rotation in a `TODO(josh)` block. There is no token table, no bearer middleware for the
public surface, and no rotation logic. `api/src/middleware/auth.ts` is the **internal** surface's
bearer path over `api_tokens` and L01's PF-010 forbids importing it — the hashing discipline is
copied by convention, not by import, the same call L02's PF-034 made and for the same reason.

## Notes for the audit agent

Read the full PRD, not just the pages cited above. Known thin spots and the calls made, so you can
confirm or refute rather than rediscover:

- **PF-171 is the one thing in this file I did not decide, and it is not a stylistic call.** L17's
  PF-509 single-flight promise is keyed on the **token store instance** — it serializes refreshes
  inside one process. L19's `ship` CLI persists to a shared file (PF-506/PF-566), so two terminals are
  two processes with one credential and, under strict family revocation, the second one logs the user
  out. That is a plausible thing for a person to do *during the demo*. My lean is a 10-second
  same-generation replay window returning the already-issued pair, because it costs nothing against
  any graded assertion — L24's PF-725 replays a long-spent `R1` after three rotations, well outside
  any window, and still gets family revocation — while strict revocation trades a real usability
  failure for a guarantee no test is measuring. The honest counter-argument is that p.3 says *"reuse
  invalidates the family"* without qualification, and a window is a documented departure from that
  sentence, the same species of thing L02's PF-048 has to write up for Stripe rotation. **Whichever
  way it lands, PF-175's Pre-Search answer has to say the same thing the code does** — that is the
  drift L25's PF-773 exists to catch.
- **PF-161's `details.reason` is a real design constraint, not a shortcut, and the audit should test
  the reasoning.** p.2 says *"expired tokens return 401 with a distinct error code"*, and the only
  401 in L07's six-code union (printed verbatim on p.7) is `unauthorized`. A seventh code would break
  a graded interface definition **and** L17's PF-498, which asserts the SDK's map is key-equal to
  `API_ERROR_CODES`. `details` is where L03's PF-069 already puts machine-readable specifics for the
  403, so this follows an established rule rather than inventing an escape. If the audit reads the
  gate clause as literally demanding a distinct `ApiErrorCode`, that is a three-lane conversation
  (L06, L07, L17) and a spine note, not an edit to this file.
- **PF-164 is new code that could easily be written the wrong way and nobody would notice.** The
  internal middleware's no-fallback behaviour (`middleware/auth.ts:135`) is what makes the CSRF skip
  at `app.ts:73` safe (L99 **F26**), and L22's PF-665 pins it there. The *public* middleware is
  written from scratch in this lane, and a helpful `if (!token) { tryCookie() }` would make the portal
  appear to work while quietly falsifying L22's dog-food claim (PF-651) and putting a CSRF-able
  credential on the public write path. This is the ticket I would most want an auditor to actually
  run rather than read.
- **The single issuance site (PF-155) is load-bearing across three lanes and is cheap to violate.**
  L04's PF-100 and L05's PF-140 both call it and both carry their own grep assertion that they mint
  nothing. If either lane grows a local `generateToken`, the two grants drift into different rotation
  semantics and PF-169's family guarantee becomes true for one flow and not the other — which would
  pass every test in this file. The grep assertions in all three lanes are the mechanism; check they
  survived.
- **What I did not re-decide.** **D8** (SDK store shape and refresh threading) is closed by L17's
  PF-504/PF-509 and this lane consumes it — PF-170 is the server half and PF-171 is the residual, not
  a reopening. **D1** (SHA-256 unsalted) is L02's and PF-152 applies the same discipline to tokens for
  the same reason `docs/architecture.md:138` already gave. **D2** (owner deleted → apps deactivated)
  is L02's and PF-156 is the boundary assertion PF-052 explicitly deferred here. **D4** (re-consent
  with union) is L04's PF-099; PF-166 asserts only that a refresh cannot **widen** scope, which is the
  same decision seen from the token endpoint.
- **`Advances` distribution and the two blanks.** `MVP-3` on seven tickets (the gate item this lane
  exists to close, jointly with L08's router composition), `CTR:Refresh Tokens` on six (p.3's row),
  `CTR:*` on five more (Token Middleware ×2, Public API Boundary ×1, OAuth App Model ×1, Consistent
