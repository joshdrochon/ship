# L02 · OAuth App Registry & Secret Lifecycle

| | |
|---|---|
| **Agent** | `oauth-apps` |
| **Tier** | 1 — runs concurrently with L03, L07 |
| **Block** | PF-031–060 (27 allocated, 3 reserved for audit) |
| **Blocks on** | L01 (PF-001 module tree, PF-008 strict TS, PF-010 boundary lint, PF-014/015/016 composition root, PF-021 migration block) |
| **Unblocks** | L04 (client authentication at `/oauth/token`), L05 (device grant client lookup), L06 (token→app resolution, `active` gating) |
| **MVP gate** | **Item 1 (p.2)** — *"admin can create an app, receive a `client_id`, and a `client_secret` hashed in the database (raw secret shown exactly once on creation)"*. This is the last unclaimed MVP checkbox board-wide. Item 10 (p.2) jointly with L21 — *"at least one OAuth app pre-registered with read-only scopes for graders"*: L21 verifies it exists in the deployed database, this lane ships the reproducible mechanism that puts it there |

**Why this lane is the first thing after foundations.** Build Strategy priority 1 (p.11): *"OAuth
foundation FIRST. Without working tokens and scope checks, nothing else has a contract."* Three
lanes cannot start until an `oauth_apps` row exists to hang a token on (L04, L05, L06), and one
already declares a foreign key into a table this lane owns (L15's PF-421, L99 dispute B3). The
table does not exist in `api/src/db/schema.sql` today.

**Three decisions arrived settled and this file builds to them.** They are D1–D3 in
`lane-99-unassigned.md`, closed 2026-08-12:

| # | Decision | Where it lands |
|---|---|---|
| D1 | `client_secret` hashed **SHA-256, unsalted** | PF-034 implements, PF-035 adds the `token_prefix`-style identifier, PF-038 proves it never leaks |
| D2 | Owner deleted → **apps deactivated** (`active=false`, tokens stop validating) | PF-051 implements, PF-052 proves the token path honors it, PF-053 is the recovery story p.17 asks for |
| D3 | Rotation → **instant invalidation** of the old secret | PF-047 implements, PF-048 writes the *documented departure* from Stripe's grace period |

**D3 is the one that owes an argument, not just an implementation.** p.17 does not ask which
model we like — it asks *"is the old secret immediately invalidated, or does it work alongside
the new one for a grace period? What does Stripe do, and why?"* Stripe offers a grace period
(0h / 1h / 24h / 3d / 7d). We ship instant, and the defense is narrow and honest: a one-week
build with no production integrations has no migration window to protect, and instant is the
model where a leaked secret is dead the moment you act. L25's PF-762 owns writing that answer;
PF-048 owns making the shipped behavior and the written answer the same thing.

**What this lane does not own.** The consent screen, the authorize/token endpoints and the PKCE
exchange (L04); the device grant (L05); token issuance, refresh rotation and the bearer
middleware (L06) — all three lane files are unwritten at the time this one was authored, so no
ticket below names an ID from them. The portal's *display* of a shown-once secret, its CSRF
regression test, and the register form itself are L22's (PF-664–670); this lane ships the
endpoints those screens call.
