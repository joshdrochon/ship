## What this is, and what it is not

PRD p.12 requires that *"each PR description lists which acceptance criterion that slice
advances and confirms the fitness test passed."*

**The per-slice review trail for this project lives in commit bodies and in this ledger, not
in per-slice merge requests.** 190 `pf/*` branches exist on `origin` (188 slices plus
2 integration branches). **7** merge requests have a `pf/L<NN>-*` branch as their
source — !21–!27 — of which **5** carry both required sections. A further 4 batch merge
requests, !17–!20, cover whole integration batches rather than single slices.

**No retroactive merge requests were opened.** Opening an MR for an already-merged branch
fabricates a review trail that never existed, and the timestamps would show it. The clause
*"each PR description"* is therefore **not met as written**, and this document does not claim
it is. What is on offer is the information the clause asks for, recovered from artifacts that
are contemporaneous with the work: the branch, the merge commit, the commit body, and the lane
file's own Slices table.

**This ledger is the inventory; `docs/pr-compliance-sweep.md` is the audit.** The sweep
measures the *quality* of those commit bodies — whether each one names its tickets and names a
test, a pass ratio or an exit code a reader can go and re-run. This file makes no quality
judgement at all: a `Fitness artifact in commit body` cell means the string appears in a commit
message, not that the artifact exists, ran, or passed.

Two further limits, stated rather than left to be discovered:

- **The `Advances` column is a claim, not proof.** It is read from the lane file's Slices table
  where one exists, and otherwise from the `Advances` column of the ticket rows the commit
  bodies name. Both were written alongside the work, not after grading it. `Source` describes
  **only** where the criterion came from — `slices-table` is the slice's own planned criterion,
  `ticket-advances` is inferred from the tickets the commits cite, and `commit-body` means
  neither source resolved anything and the cell is `—`. It says nothing about the two fitness
  columns, which are filled independently wherever the data exists.
- **`fast-forward / squashed` rows carry less evidence than merged rows.** With no merge commit
  to bracket, the slice's own commits cannot be recovered as `P1..P2`; the tip commit alone is
  read instead. For a squashed branch that is the whole slice. For a fast-forwarded one it is
  the last commit only, so those rows can under-report tickets and artifacts.
