## 2. The pre-registered apps (PF-630)

Three OAuth apps are seeded by `seedPlatformApps()` (`api/src/db/platformApps.ts`), which
runs on **every** `db:migrate` — and `db:migrate` runs in the container's `CMD` on every
boot. That is the answer to p.17's *"what guarantees it exists in deployed
environments?"*: not a one-time migration, and not a manual step, but the same schedule
as the migrations themselves.

The distinction matters and L02 wrote it down: a numbered `.sql` migration runs **once**
per database, so an app seeded that way would never pick up a secret set after the first
deploy, and a rotated secret would never be written. Migration 041 keeps only the
one-time structural rows (the system user, the grader workspace); the app upsert is
`ON CONFLICT (client_id) DO UPDATE` and re-runs every time.

| App | `client_id` | Scopes | Purpose |
|---|---|---|---|
| Grader (read-only) | `ship_app_grader_readonly` | `documents:read`, `issues:read`, `sprints:read` | MVP gate item 10. **Read-only, exactly** — p.2 puts "read-only scopes" in the gate checkbox itself. A test asserts no scope ends in `:write`. |
| Grader demo | `ship_app_grader_demo` | read + write | L99 **D12**. See §4. |
| FleetGraph Agent | `ship_app_firstparty_fleetgraph_agent` | `documents:read`, `issues:read`, `issues:write`, `sprints:read` | First-party, Epic 7. Not for graders. |

**Tenancy — p.18's "without exposing your tenant's data."** The grader apps belong to a
dedicated workspace (`GRADER_WORKSPACE_ID`, a fixed UUID) owned by a dedicated seeded
user (`platform-apps@ship.local`), not the primary account. A token issued to a grader
app sees that workspace and no other.

**Secrets.** The three `client_secret` values are generated by Terraform
(`terraform/platform-apps.tf`) and stored as SSM `SecureString` parameters under
`/ship/dev/`. They are read back with:

```bash
cd terraform && terraform output -raw grader_client_secret
# or
aws ssm get-parameter --name /ship/dev/GRADER_CLIENT_SECRET --with-decryption \
  --query Parameter.Value --output text
```

These are deliberately **recoverable**, which looks like a contradiction of
Implementation Rule 11 ("shown exactly once, never recoverable") and is not. Rule 11
governs secrets issued *to a user* through the dev portal, where the one-time display is
the security property. These are machine credentials that the README itself has to
publish (p.13 requires "credentials in the README"), so a value nobody can read back
would make the deliverable impossible. The two cases are different and the codebase
treats them differently.

## 3. URL stability decision (PF-632)

### The measured situation

- `cname_prefix` is **not set** in `terraform/elastic-beanstalk.tf`. The environment's
  CNAME suffix (`eba-nvpntpge`) is AWS-generated. Recreating the environment produces a
  **different, unpredictable** name and there is no way to ask for the old one back.
- This has already happened once on this project. `.claude/CLAUDE.md` still documents the
  prod API as `ship-api-prod.eba-xsaqsg9h.us-east-1.elasticbeanstalk.com`; the live
  environment answers on `eba-nvpntpge`. The documented URL is dead and nothing noticed.
- The RDS endpoint host changes on cluster replacement **regardless** of any of this. It
  is not a published link, so it costs a config update rather than a broken submission.
- `.gitlab-ci.yml` carries a `doc-links` job precisely because `SUBMISSION.md` once
  linked a service that had been torn down while every other check stayed green. It is
  the only check in CI that leaves the runner. **Keep it under every option below.**

### Options

| # | Option | Survives env replacement? | Cost to adopt | Notes |
|---|---|---|---|---|
| a | Publish the bare EB CNAME (status quo) | **No** — and the replacement name cannot be predicted or pinned | Zero | What is published today |
| b | Set `cname_prefix` | Yes, if the prefix is still free | **Forces environment replacement** | `cname_prefix` is ForceNew. Adopting it *causes* the outage it prevents, and the destroy guard blocks it for that reason |
| c | Front the API with the existing CloudFront distribution | **Yes** — CloudFront domains outlive their origins | One variable | `var.eb_environment_cname`; the API origin, cache policy and behaviours are already written and gated on it |
| d | Custom domain + ACM | Yes, completely | Needs a registrable domain and a Route 53 zone | `var.app_domain_name` / `var.route53_zone_id`, both empty; no domain is available for this project |

### Decision, and my lean

**Recommended: (c).** It is the only option that closes the risk without either causing
an environment replacement or requiring a domain we do not have, and the work is
genuinely one variable — `s3-cloudfront.tf` already declares the EB origin, an
`api_no_cache` cache policy and five behaviours, every one of them `for_each`-gated on
`var.eb_environment_cname != ""`. Setting it publishes the spec at
`https://d258p92d3n1ebe.cloudfront.net/api/v1/openapi.json`, which survives an EB
environment being destroyed and rebuilt — the exact scenario PF-642's drill exercises and
the exact scenario that already broke a submitted URL once.

It also upgrades the published URL from `http` to `https`, which the bare EB CNAME cannot
offer without an ACM certificate and therefore a domain.

**(b) is a trap and should be named as one at the defense.** Pinning the CNAME sounds
like the obvious fix and is the one option that *guarantees* the outage — `cname_prefix`
forces replacement of `aws_elastic_beanstalk_environment`, so adopting it destroys the
environment whose name it was meant to protect.

**What is published today is (a).** That is a deliberate sequencing choice, not an
endorsement: gate item 10 is pass/fail on Friday and the CloudFront change touches the
distribution serving the frontend, so it is not something to apply untested at the same
moment as the first successful application deploy. **This is the open call for the
coordinator:** adopt (c) before the URL goes in `SUBMISSION.md`, or accept (a) and accept
that the drill must never touch the graded environment.

### Everything that depends on the choice

Change the published base URL and all of these move together:

| Spec URL | `docs/infra/grader-access.md` §1, README | Gate item 10 fails on a 404 |

## 4. D12 — the grader cannot run the demo (open, mitigated)

p.6's five-line story is `ship login` → `ship docs create` → `ship webhooks tail`, and
p.12/p.13 make that story the demo video and the Social Post. The grader's app is
**read-only by requirement** (p.2), so a grader following the README cannot run the
headline command.

**Resolution shipped: a second, write-scoped app** (`ship_app_grader_demo`, PF-057),
which is L99's recommended option. The README must be explicit about which credential to
use for which step — a grader who reaches for the read-only app and gets a 403 on
`ship docs create` will read it as a broken demo rather than as the security property it
is.

The alternative L19 already documents (`ship docs ls` as the grader smoke test, PF-580)
remains true and is the fallback if the demo app is judged to widen the graded surface
too far. Widening the grader app's own scopes was rejected: it would make the gate
checkbox literally false.
