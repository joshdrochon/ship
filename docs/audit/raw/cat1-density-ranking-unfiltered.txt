RANKING RULES, ALL THREE STATED
  1. Density = violations per 100 LOC, as emitted by the script's /100 column.
  2. Files under 200 LOC are excluded from density rankings. This is the report's existing
     stated rule and it is a real one: a 20-line file with 3 casts scores 15/100 and means
     nothing. 93 of the 144 files carrying a violation at baseline clear 200 LOC.
  3. "Production only" excludes any path containing __tests__, .test. or .spec.
     THIS IS THE RULE THAT WAS APPLIED WITHOUT BEING DECLARED.
     It reproduces the report's own production/test split exactly — 803 violations in 123
     production files, 206 in 21 test files at baseline — so it is the same definition the
     report already uses elsewhere, just never named at the table.

WHY THE DISTINCTION MATTERS
  A test file's `any` is usually a mock or a fixture: `const req = {} as any` standing in
  for a request the test does not care about. That is a legitimate use — the alternative
  is constructing a full object to satisfy a type nothing under test depends on. Production
  code has no equivalent excuse; there every `any` and every `as` is a claim about real
  runtime data that the compiler has been told not to check.
  So the production-only ranking IS the more useful one for deciding what to fix. That was
  a defensible editorial choice. Publishing it as "the top 5 densest files" without saying
  so was not, because the reader cannot tell that three rows were removed.

  Note also that the two rankings disagree about kind, not just order: the top two files
  in the codebase by density are both test files, and both are denser than anything in
  production. A reader shown only the filtered table would conclude the opposite.
